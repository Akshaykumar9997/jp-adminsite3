# Media uploads and deletion

The subsequent One UI-inspired gallery update replaces exposed content/media
deletion with Trash followed by optional permanent deletion. See
`docs/gallery-verification.md` for the required migration and new restore rules.

Implemented shared deletion confirmation and cache eviction for rooms, works,
materials, partners and media. Uploaded assets are removed from the global queue
when deleted, so queue history cannot recreate deleted cards. Concurrent requests
for the same deletion share one operation. Failed or blocked deletes preserve
the editor and its data for retry.

Deleting content keeps reusable media. Database foreign keys continue to block
deleting files still in use or rooms with existing works. After a confirmed media
deletion, a storage failure is reported as a cleanup warning, not a failed database
deletion. Pending cleanup paths survive reload in localStorage and can be retried
from Media Library. Cleanup skips paths reserved by active uploads and files with
existing metadata. If browser storage is disabled, cleanup retries remain available
for the current session only.

The global upload panel stays at the bottom-right, including while dialogs are
open. It supports two concurrent transfers, further queued files, additional batches,
collapse, cancellation, retry, and completed/failed/cancelled results. Closing the
panel during an active upload only collapses it. Progress uses actual XHR transfer
events; database registration is a separate finishing stage. Estimated time is based
on observed transfer speed. Completed files release their in-memory file bytes.
The reviewed Drive-style tray uses 56px file rows, blue circular progress (no
horizontal bars), a pale time-left/Cancel strip and green completion checks.
Queued files use grey rings; preparation/registration use indeterminate rings.
Transfer percentages stop at 99% in the ring until metadata is confirmed; only then
does the green check appear. Per-file cancellation is on the circular indicator
(hover/focus exposes the cancel icon); failed/cancelled rows retain Retry/Remove.
`npm run test:upload-panel` exercises numeric ring progress, completion guards,
video rows, ETA, collapse/navigation/dismiss and 320/390/768/1440 layouts.
Failed metadata registration checks for an already committed asset before cleanup,
so a lost response does not destroy a successfully uploaded file. Retried cancelled
uploads reattach to the originating open editor.

Uploads continue across client-side Admin site navigation. Refresh, browser closure, or
computer shutdown cannot continue this in-memory queue; active uploads trigger
the browser's leave-page warning. This is not a resumable upload implementation.
Cancellation and cleanup are best effort when the server cannot be reached. Files
uploaded from an editor remain reusable in Media Library if the editor is abandoned;
the unsaved content itself is not automatically saved.

## Verification

- `npm run test:media`: deletion unit checks and Chrome workflow checks using the
  disposable local PostgreSQL/Storage server. Covers duplicate-delete locking,
  failed/zero-row/in-use deletion, media card eviction without refresh, cleanup
  retry after refresh, content deletions and reusable media preservation, queue
  concurrency and new batches across navigation, cancel/retry and editor
  reattachment, metadata write failure and lost-response recovery, file validation,
  modal positioning, and 320/390/768/1440px layouts.
- `npm run test:browser`: existing gallery/editor/navigation regression coverage.
- `npm run test:next`: existing unit and disposable database checks including RLS.
- `npm run build`: TypeScript and production bundle verification.
- `npm run test:security`: client and bundle secret scan.

Browser tests require Playwright/Chrome, the disposable backend at port 54321, and
Vite at port 5174 configured with `VITE_SUPABASE_URL=http://127.0.0.1:54321` and
`VITE_SUPABASE_PUBLISHABLE_KEY=local-publishable-test-key`. Start the backend with
`npm run test:local-server`; start Vite with `npm run dev -- --host 127.0.0.1 --port
5174 --strictPort`. Playwright was supplied by the desktop bundled runtime using
`NODE_PATH`, without adding a project dependency. Tests refuse a non-disposable
frontend configuration. Source changes have not been deployed or tested against
the hosted production backend. The original deletion/upload patch required no
schema migration; the subsequent Trash/gallery update does require one.
